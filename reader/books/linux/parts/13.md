# Código com Git no Linux
## Histórico de mudanças
Git registra versões de arquivos e permite comparar, recuperar e colaborar. Um repositório local funciona sem internet. Crie `~/laboratorio-linux/projeto-git`, entre nele e execute `git init`. Confirme com `git status`. Não inicie Git na pasta pessoal inteira: poderia rastrear dados privados e produzir um histórico grande e difícil de revisar.
## Primeiro commit
Crie `README.md` descrevendo o projeto. `git add README.md` prepara a mudança; `git diff --cached` mostra exatamente o que será registrado; `git commit -m "Inicia projeto"` cria o ponto no histórico. Configure nome e email conforme seu contexto, sem usar dados de outra pessoa. Um commit deve explicar uma mudança coerente, não apenas “arquivos”.
## Compare versões
Edite o README, rode `git diff` para ver alterações não preparadas e `git status` para entender estados. Depois prepare e faça segundo commit. `git log --oneline` mostra a sequência; `git show` detalha um commit. Não use comando de descarte até saber se o trabalho pode ser recuperado. A diferença entre arquivo, índice e histórico é central.
## Ramos para experimentar
`git switch -c experimento` cria ramo para uma ideia. Faça alteração pequena e commit, depois volte ao ramo inicial com `git switch`. Arquivos modificados sem commit podem impedir troca ou acompanhar você; verifique `git status` antes. Um ramo não é cópia independente de toda a pasta, e mesclar trabalho exige resolver eventuais conflitos.
## Remotos e cuidado
Um remoto é endereço de outro repositório; `git remote -v` lista os configurados. Enviar com push publica commits para quem tem acesso ao destino. Antes, revise histórico, `.gitignore`, arquivos grandes e segredos. Remover uma chave do último arquivo não elimina cópias no histórico remoto. Em caso de exposição, revogue a chave no serviço emissor.
## Colaboração legível
Commits pequenos, mensagem clara, revisão de diff e instruções de execução facilitam manutenção. Num projeto compartilhado, abra uma proposta de mudança, descreva teste e peça revisão conforme fluxo adotado. Não misture formatação massiva com correção urgente sem motivo. Git registra o que mudou; o README e a discussão explicam por que a mudança é útil.
## Verifique
Crie dois commits no repositório de treino e mostre `git log --oneline`. Indique qual versão do README está no índice e qual está apenas no diretório de trabalho. Faça um ramo de experimento e volte sem perder alterações. Explique por que revisar `git diff --cached` antes do commit reduz erros.

# Linguagens e ferramentas de desenvolvimento
## Compilar ou interpretar
Programas podem ser compilados em executável, interpretados ou usar combinações dessas etapas. O Linux oferece compiladores, interpretadores, bibliotecas e depuradores por pacotes. `command -v gcc`, `command -v python3` e `command -v node` mostram quais ferramentas estão disponíveis, sem instalá-las. Escolha uma linguagem para o exercício; entender ambiente importa mais que possuir todas.
## Primeiro programa C
Se o compilador estiver instalado, escreva um programa mínimo que imprime “Olá”. Use `gcc -Wall -Wextra -o ola ola.c`, depois `./ola`. Avisos ajudam a encontrar problemas, mas compilação bem-sucedida não prova comportamento correto. Não execute binários recebidos de origem desconhecida. Se não houver compilador, leia o comando e planeje instalação por repositório oficial.
## Biblioteca e pacote
Uma aplicação depende de bibliotecas e versões. `ldd` pode mostrar dependências dinâmicas de um binário confiável, mas não execute `ldd` em arquivo não confiável: certos contextos podem ter efeitos inesperados. Prefira inspeção controlada com ferramentas documentadas. Gerenciador de pacotes da distribuição resolve dependências de sistema; projetos de linguagem podem ter gerenciadores próprios.
## Editor e terminal
Editor, terminal e Git formam um fluxo básico: editar, executar teste, examinar diff, registrar. Use editor confortável, com destaque de sintaxe e leitura de arquivos UTF-8. Extensões têm acesso ao projeto e podem executar código; instale somente as necessárias e de origem confiável. Configure indentação consistente e mantenha arquivos de configuração do projeto versionados quando apropriado.
## Erro reproduzível
Ao reportar um bug, forneça versão, comando, entrada mínima, resultado esperado e observado, sem segredos. Reduza o caso até retirar tudo que não causa falha. `python3 --version` ou a ferramenta equivalente ajuda a registrar ambiente. Um erro intermitente exige data e condições. A boa investigação separa falha do programa de pacote, configuração e sistema.
## Depuração gradual
Imprimir valores pode esclarecer fluxo simples; um depurador permite pausar e inspecionar estados mais complexos. Logs devem informar contexto sem vazar dados. Comece com teste que reproduz erro; corrija e rode novamente. Não faça mudanças em cinco lugares ao mesmo tempo. A mesma disciplina usada para diagnosticar rede e serviços serve para programa.
## Verifique
Escolha uma linguagem disponível na VM, faça programa “Olá” e registre como executá-lo em outra instalação. Liste dependências e versões. Introduza um erro deliberado, guarde a mensagem e corrija após formular hipótese. Faça commit do código e de instruções, excluindo binários e dados gerados quando não forem necessários.

# Python e ambientes isolados
## Sistema e projeto
O Python instalado pela distribuição pode sustentar ferramentas do sistema. Instalar pacotes de terceiros diretamente nele pode conflitar com gerenciador da distribuição. Para cada projeto, use ambiente virtual. `python3 -m venv .venv` cria um na pasta do projeto quando o módulo está disponível; consulte pacote de venv da distribuição caso falhe.
## Ativar e inspecionar
`source .venv/bin/activate` ajusta PATH do shell atual; `command -v python` deve apontar para o ambiente. `python -m pip --version` mostra qual pip está em uso. Você também pode chamar `.venv/bin/python` diretamente, sem ativar. A ativação não muda todos os terminais, nem instala algo globalmente. Use `deactivate` para sair do ambiente ativado.
## Dependências explícitas
Instale bibliotecas necessárias no ambiente a partir de fonte confiável. `python -m pip list` mostra o conjunto atual. Um arquivo de dependências ou projeto deve declarar versões ou intervalos adequados para reprodução. Não copie a pasta `.venv` entre sistemas como único método de implantação. Registre instruções para recriá-la e teste numa VM limpa.
## Programa pequeno
Crie `contagem.py` que lê um arquivo de treino e conta linhas. Use biblioteca padrão, `pathlib.Path`, tratamento de arquivo ausente e impressão de erro compreensível. Passe caminho por argumento. Teste arquivo vazio e nome com espaço. Não use `sudo pip` nem altere pacotes globais para rodar um script simples. O mesmo raciocínio aplica-se a outras linguagens.
## Ferramentas de projeto
Formatadores, linters e testes automatizados podem ser dependências de desenvolvimento. Escolha poucos, configure-os no repositório e execute antes do commit. Um teste útil verifica comportamento observável, como contagem correta para arquivo vazio; teste que apenas repete a implementação dá pouca confiança. Documente como executar as verificações no README.
## Atualização com critério
Bibliotecas mudam e podem corrigir falhas ou quebrar interfaces. Leia notas de versão, atualize em ramo, rode testes e revise diferença de dependências. Não fixe versões para sempre sem rotina de revisão, nem atualize tudo cegamente em produção. Separe atualização de aplicação de atualização do próprio sistema operacional para diagnosticar eventuais problemas.
## Verifique
Crie ambiente virtual na VM, confirme o caminho do Python e execute `contagem.py` sem instalar pacotes externos. Teste arquivo vazio, três linhas e arquivo ausente. Escreva instruções para outra pessoa recriar o ambiente. Explique por que instalar bibliotecas do projeto no Python do sistema pode causar conflito.

# Serviços, contêineres e nuvem
## De script a serviço
Uma aplicação web precisa de processo duradouro, configuração, logs, rede, atualização e recuperação. O script que funciona no terminal não se torna automaticamente serviço confiável. Desenhe entrada HTTP, aplicação, banco de dados, arquivos e backup. Identifique dono de cada dado e modo de recuperação. Publique primeiro em laboratório ou ambiente de teste controlado.
## Configuração fora do código
Endereço de banco, chave e modo de execução variam por ambiente. Separe configuração do código e proteja segredos com mecanismo adequado. Não confie em valor padrão inseguro. Documente variáveis necessárias sem incluir valores secretos. Na VM, simule duas configurações com arquivos de treino e confira que o programa informa ausência de uma variável obrigatória.
## Imagem reproduzível
Uma imagem de contêiner pode empacotar aplicação e dependências. Escolha base mantida, versão explícita, usuário com privilégio mínimo e arquivos indispensáveis. Não copie `.env` ou chave privada para a imagem. Teste o resultado e revise vulnerabilidades conforme ferramenta e política do projeto. O arquivo de construção descreve passos; o digest identifica imagem concreta produzida.
## Estado fora do processo
Contêineres podem ser substituídos; dados duráveis precisam de volume ou serviço externo com backup. Se aplicação guarda uploads dentro da camada efêmera, recriar contêiner pode perdê-los. Banco de dados exige migração e recuperação próprias. Desenhe ciclo de vida de uma foto enviada e de um registro, do navegador ao backup. Isso revela o que precisa persistir.
## Nuvem é outro computador
Servidores de nuvem continuam exigindo atualização, contas, rede, logs, backup e orçamento. O provedor administra algumas camadas, e você administra outras conforme serviço contratado. Verifique modelo de responsabilidade documentado. Não deixe laboratório ligado indefinidamente: recursos podem custar dinheiro. Para aprender conceito, VM local é suficiente e oferece controle de custos.
## CI com limites
Integração contínua executa testes após mudanças. Defina trabalho mínimo: instalar dependências, validar formatação, rodar testes, produzir artefato. Um pipeline pode acessar segredos e publicar versões; proteja permissões, revisões e ambientes. Passar no CI significa que verificações definidas passaram, não que todo comportamento real foi provado. Inclua teste manual de função crítica antes de implantação.
## Verifique
Desenhe implantação simples com aplicação, dado persistente, backup e monitoramento. Aponte quais partes podem ser recriadas e quais não podem se perder. Explique por que segredos não devem entrar na imagem. Escreva pipeline conceitual de três etapas e um teste manual necessário antes de publicar.

# Participar do ecossistema
## Muitas comunidades
Linux inclui kernel, distribuições, ambientes gráficos, bibliotecas e inúmeros projetos independentes. Cada um tem mantenedores, licença, regras e canais próprios. Um bug de navegador pode não pertencer ao kernel. Antes de abrir relato, encontre projeto correto, versão e instrução para reportar. Ser específico aumenta chance de uma resposta útil e respeita tempo de voluntários.
## Leia a fonte oficial
Notas de versão, manuais da distribuição, páginas `man` e documentação do projeto têm prioridade para comportamento atual. Fóruns ajudam com exemplos, mas podem refletir versões antigas. Inclua distribuição, versão e comando exato ao pedir ajuda. Cuidado com sugestões que desativam segurança ou apagam dados. Teste comandos em VM e compreenda cada argumento antes de usar.
## Contribuir de várias formas
Você pode melhorar tradução, documentação, acessibilidade, testes, relato de bugs, design e código. Comece com mudança pequena e alinhada ao guia do projeto. Leia licença e código de conduta. Uma contribuição não precisa ser extensa para ser valiosa; uma instrução corrigida pode poupar horas a quem está chegando.
## Relato verificável
Um bom bug report traz passos para reproduzir, esperado, observado, versão, logs relevantes e tentativas feitas. Redija sem dados pessoais, tokens ou despejos completos de sistema. Se só ocorre no seu computador, descreva hardware e configuração pertinentes. Aceite que mantenedores podem pedir teste adicional; essa conversa ajuda a localizar causa.
## Aprender continuamente
Reserve prática regular: leitura de documentação, laboratório descartável, pequeno projeto e revisão do que funcionou. Escolha trilha conforme interesse: administração, desenvolvimento, segurança, desktop, ciência de dados, sistemas embarcados. Fundamentos de arquivos, processos, permissões e rede reaparecem em todas. Não tente decorar todos os comandos; aprenda a encontrá-los, avaliar risco e testar.
## Ética operacional
Experimente apenas em máquinas e redes suas ou autorizadas. Respeite dados e privacidade de outras pessoas, documente mudanças e deixe caminho de recuperação. Saber usar uma ferramenta poderosa inclui saber quando não executá-la. Ao ensinar alguém, explique intenção, efeito esperado, modo de conferir e como desfazer. Essa clareza mantém a comunidade acessível a iniciantes.
## Verifique
Escolha projeto livre que usa Linux e leia seu guia de contribuição. Escreva relato fictício de bug com versão e passos, sem dados sensíveis. Liste uma contribuição não ligada a código. Monte plano de 30 dias para continuar: uma prática por semana, um pequeno projeto e um modo de verificar o que aprendeu.

# Projeto final e mapa do futuro
## Uma VM explicável
O projeto final é preparar uma VM Linux para uso pessoal de laboratório. Documente distribuição e versão, instalação, contas, atualizações, estrutura de pastas e backup. Crie arquivo de inventário com comandos de leitura. A meta é que outra pessoa entenda e reproduza o ambiente, não que ele tenha a maior quantidade de programas.
## Um serviço pequeno
Publique a página de laboratório apenas em localhost e com usuário comum. Confirme porta, resposta HTTP, processo e log. Descreva o que faltaria para servir publicamente: domínio, TLS, proxy, atualização, controle de acesso, firewall, monitoramento e backup conforme necessidade. Não coloque servidor didático na internet para obter “nota” no exercício.
## Uma automação revisada
Inclua `relatorio-vm.sh` do capítulo de Bash com testes de entrada e mensagens claras. Guarde código em Git sem segredos e registre dois commits significativos. Mostre status limpo e instruções de execução. Se decidir agendar, faça somente na VM e explique como desligar. A automação deve continuar legível para você depois de um mês.
## Um cenário de falha
Crie falha reversível, como renomear o arquivo HTML de treino. Observe erro, formule hipótese, veja logs, restaure arquivo e confirme a volta. Registre linha do tempo e evidência. Não simule perda de dados reais nem derrube rede compartilhada. A capacidade de recuperar vale tanto quanto a de configurar pela primeira vez.
## Rubrica de conclusão
Verifique se você consegue explicar boot, arquivos, permissões, pacotes, processos, rede, segurança e backups com exemplos próprios. Mostre uma prática de cada eixo e seus resultados. Onde você não consegue explicar o porquê, marque para revisão. “Funciona na minha VM” é começo; documentação, teste e recuperação mostram domínio mais maduro.
## Próximas trilhas
Para administração, aprofunde systemd, rede, armazenamento e monitoramento. Para desenvolvimento, estude linguagem, testes e implantação. Para segurança, aprenda modelos de ameaça, auditoria e resposta. Para kernel, avance em C, arquitetura e depuração. Escolha uma trilha por vez e mantenha fundamentos vivos. Leia documentação atual da distribuição quando detalhes de comandos mudarem.
## Verifique
Apresente a VM, o relatório, o repositório e o registro de recuperação a alguém iniciante. Peça que repita uma etapa só com suas instruções e corrija ambiguidades. Escreva três coisas que já consegue fazer sem copiar comandos e três que ainda precisa consultar. O objetivo final é autonomia cuidadosa, não memorização de cada detalhe do Linux.
