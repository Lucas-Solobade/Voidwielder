# Arquivos, JSON e CSV
## Caminhos com pathlib
`pathlib.Path` representa caminhos sem precisar montar separadores manualmente. `Path("dados") / "notas.txt"` constrói um caminho relativo. Relativo a quê? Ao diretório de trabalho do processo, que pode mudar conforme terminal, serviço ou teste. Em projeto real, escolha uma base explícita. Antes de ler ou sobrescrever, confira o caminho resolvido e não aceite entrada de usuário como caminho irrestrito para dados sensíveis.
## Ler texto
```python
from pathlib import Path
texto = Path("notas.txt").read_text(encoding="utf-8")
print(texto)
```
Para arquivo pequeno, essa forma é clara. Arquivo grande pode exigir leitura linha a linha: `with caminho.open(encoding="utf-8") as arquivo:`. O bloco `with` fecha o arquivo mesmo quando surge exceção. No laboratório do navegador, arquivos existem apenas no sistema virtual daquela sessão, não no disco do visitante.
## Escrever sem perder dados
`write_text` substitui conteúdo existente. Antes de gravar, defina se o comportamento correto é criar, substituir ou acrescentar. Para operação importante, grave em arquivo temporário no mesmo volume e renomeie após sucesso, conforme necessidade de durabilidade. Backups continuam necessários. Uma mensagem “salvo” só deve aparecer depois que a escrita terminou sem erro. Teste falha de permissão e arquivo vazio.
## JSON estruturado
`json.dumps(dados, ensure_ascii=False)` transforma estruturas compatíveis em texto JSON; `json.loads(texto)` faz o caminho inverso. JSON é formato de dados, não código Python: tem `true`, `false` e `null`. Nem todo objeto Python pode ser serializado diretamente. Valide campos e tipos recebidos de arquivo ou API. Um JSON sintaticamente válido ainda pode faltar a chave que seu programa exige.
## CSV exige biblioteca
O módulo `csv` lida com delimitadores, aspas e quebras de linha. Não use `linha.split(",")` para planilha real: uma célula pode conter vírgula entre aspas. Abra arquivo com `newline=""` e codificação conhecida. `csv.DictReader` mapeia cabeçalhos para valores textuais. Converta números de modo explícito e trate linhas incompletas. Em fontes brasileiras, delimitador pode ser ponto e vírgula.
## Formatos e confiança
Arquivo recebido de outra pessoa pode ser grande, inválido ou conter dados maliciosos. Limite tamanho, use parser adequado e não execute conteúdo de arquivo como Python. `pickle` é conveniente para objetos Python, mas carregar um pickle de origem não confiável pode executar código; não o use como formato público. Para intercâmbio simples, JSON ou CSV com validação são escolhas mais transparentes.

Na atividade, receba um texto JSON com lista de valores e devolva a soma; inclua tratamento para formato inválido. Explique por que a vírgula dentro de uma célula quebra uma divisão manual por `split`.

# Exceções e falhas compreensíveis
## Erro é parte do contrato
Abrir arquivo inexistente, converter texto ruim e dividir por zero são situações previsíveis. Python sinaliza muitas delas com exceções. Um `try` envolve a operação que pode falhar; `except` trata uma classe específica. Não envolva o programa inteiro num `except Exception: pass`: isso esconderia bugs. Decida quais falhas você consegue resolver e quais devem subir para uma camada que conhece o contexto.
## Trate especificamente
```python
def ler_inteiro(texto):
    try:
        return int(texto)
    except ValueError:
        return None
```
O contrato diz que texto inválido devolve `None`. Isso pode ser útil, mas perde detalhe do erro; em outra aplicação, talvez seja melhor levantar exceção com mensagem. Teste `"12"`, `" "` e `"doze"`. Não capture `TypeError` sem saber se valor não textual também é entrada esperada.
## else e finally
`else` de `try` roda quando não houve exceção naquele bloco; `finally` roda ao sair, inclusive após falha, e serve para limpeza. Frequentemente `with` simplifica fechamento de arquivos. Evite colocar `return` em `finally`, pois pode esconder uma exceção anterior. Desenhe o caminho de sucesso e de falha para entender onde cada bloco executa. Clareza vale mais que usar todas as cláusulas.
## Lance uma exceção útil
`raise ValueError("quantidade deve ser não negativa")` declara que a entrada viola regra. Valide no ponto em que o contrato é conhecido. Não exponha detalhes internos sensíveis em mensagens ao usuário final; registre contexto técnico de forma protegida e apresente orientação compreensível. Diferencie falha do usuário, do ambiente e bug do código, porque cada uma pede solução diferente.
## Preservar causa
Se você traduz uma exceção para outra camada, `raise ErroDePedido("...") from exc` preserva a causa para depuração. Não transforme toda exceção em “algo deu errado” sem log. Em sistemas empresariais, rastros de erro ajudam suporte, mas podem conter dados pessoais. Registre identificador de operação e tipo de falha sem capturar segredos. A interface deve dizer o que a pessoa pode fazer em seguida.
## Tentar novamente com critério
Falhas transitórias de rede podem justificar nova tentativa com limite e espera. Entrada inválida, autenticação negada e arquivo ausente em geral não se resolvem repetindo indefinidamente. Um bot sem limite pode gerar pedidos duplicados. Antes de repetir, pergunte se a operação é idempotente, isto é, se fazê-la duas vezes tem o mesmo efeito que uma. A resposta orienta automação segura.
## Verifique e pratique
Escreva função que converte uma idade textual e rejeita número negativo. Teste válido, vazio, letras e negativo. Na atividade, trate divisão por zero com resposta clara, sem capturar exceções não relacionadas. Explique quando retornaria `None` e quando levantaria `ValueError`, considerando quem chama a função.

# Testes, depuração e qualidade
## Um teste é uma hipótese
Teste automatizado chama código com entrada e compara resultado com expectativa. Para `dobro(3)`, esperamos 6. Bons testes cobrem comportamento importante e fronteiras, não apenas a linha feliz. Uma função pode passar num exemplo e falhar para zero ou negativo. Escreva expectativa antes da implementação quando a regra estiver clara; isso evita adaptar teste para confirmar um erro existente.
## pytest e assert
```python
def dobro(valor):
    return valor * 2

def test_dobro():
    assert dobro(3) == 6
    assert dobro(0) == 0
```
`pytest` encontra funções `test_` quando instalado no ambiente de desenvolvimento. No laboratório, o botão “Corrigir” usa testes semelhantes, executados separadamente do código do site. Uma aprovação indica que aqueles casos passaram; não prova ausência de todos os bugs possíveis.
## Depure o estado
Quando um teste falha, leia entrada, saída esperada e obtida. Use `print` temporário ou depurador para observar variáveis em pontos específicos. Reduza o exemplo que falha. Não altere a função e o teste ao mesmo tempo sem entender a regra. Se o valor já está errado antes da linha suspeita, investigue a origem. Se o teste está errado, corrija a expectativa com justificativa.
## Tipos como documentação
Anotações `list[int]`, `str | None` e `dict[str, float]` ajudam ferramentas e leitores. Um verificador estático pode encontrar incompatibilidade antes da execução. Python normalmente não impõe essas anotações em tempo de execução; entrada de API ainda precisa de validação real. Use tipos para explicar contratos, não para decorar todo objeto. Em projeto grande, padronize nível de rigor com a equipe.
## Formatação e lint
Formatadores padronizam espaços, aspas e quebras. Linters apontam código não usado, imports duplicados e alguns erros. Rode essas ferramentas em mudanças pequenas para revisão clara. Uma ferramenta sem aviso não garante algoritmo correto; testes e revisão de regras continuam necessários. Evite dedicar horas a estilo de uma função que ainda não entrega o resultado esperado.
## Teste integração
Teste unitário isola função; integração verifica colaboração entre arquivo, banco, API ou serviço. Para uma função que salva pedido, simule dependências ou use ambiente de teste descartável. Não rode testes destrutivos contra banco real. Separe configuração de produção e laboratório. Um teste de ponta a ponta confirma uma jornada visível, mas é mais lento e pode falhar por motivos externos.
## Verifique e pratique
Crie três testes para uma função de desconto: preço zero, limite exato e valor inválido. Na atividade, corrija uma função com bug de fronteira e use o feedback para localizar o caso que falhou. Explique por que cobertura de linhas não substitui testar regras e por que testes de integração precisam de dados descartáveis.
