# Consumir APIs com HTTPX
## O que uma API oferece
Uma API HTTP recebe solicitações e devolve respostas, frequentemente JSON. Para usar uma, leia documentação de URL, método, parâmetros, autenticação, limite de chamadas e erros. `GET` costuma consultar; `POST` geralmente cria ou aciona operação, mas cada serviço define o contrato. Não teste escrita numa conta real por curiosidade. Comece com API pública de treino ou com servidor local sob seu controle.
## Primeira consulta
```python
import httpx

resposta = httpx.get("https://example.org", timeout=10.0)
resposta.raise_for_status()
print(resposta.status_code)
```
Instale `httpx` no projeto com `uv add httpx`. `raise_for_status` transforma respostas de erro em exceção. Para JSON, use `resposta.json()` e valide campos. O exemplo faz rede e não roda no corretor do navegador; ali o exercício usa um dicionário que imita a resposta para praticar a lógica sem depender de serviço externo.
## Timeout e falhas
Sem limite, um bot pode ficar preso esperando resposta. HTTPX usa timeout por padrão, mas configure conforme aplicação e trate erros de conexão. Diferencie 404, 429, 500 e falha de rede; repetir imediatamente todas é inadequado. Em 429, leia orientação de limite do serviço. Uma resposta HTTP 200 também pode conter dados incompletos. Valide conteúdo antes de gravar ou comunicar resultado.
## Cliente reutilizável
`with httpx.Client(timeout=10.0) as cliente:` reaproveita conexões em múltiplas chamadas. Evite criar um cliente novo por item numa lista grande. No modo assíncrono, `httpx.AsyncClient` combina com `asyncio`, mas exige fechar recurso. Não escolha async para uma única chamada simples. Uma camada pequena de cliente pode centralizar base URL, autenticação e tratamento de erro para o resto da aplicação.
## Paginação e limites
APIs frequentemente devolvem páginas de resultados. O cliente precisa seguir cursor ou número de página até condição de término, com limite de segurança. Não assuma que “menos itens que o tamanho solicitado” sempre significa fim; siga contrato oficial. Faça logs de página e quantidade sem expor dados privados. Teste resposta vazia, cursor repetido e erro após algumas páginas para evitar laço infinito.
## Segredos e permissões
Tokens de API são credenciais. Guarde-os fora do repositório, conceda apenas escopos necessários e rotacione quando expostos. Nunca embuta token em exemplo público ou URL compartilhada. Antes de automatizar mensagens, pagamentos ou alterações de dados, confirme que o serviço e o usuário autorizaram a operação. Código que consegue chamar API não implica permissão para usá-la em qualquer conta.
## Verifique e pratique
Leia documentação de uma API de treino e escreva método, URL, entrada, saída, erros e limite. Na atividade interativa, transforme um JSON simulado em lista de títulos, ignorando registros sem título com regra explícita. Depois reproduza localmente com HTTPX numa API autorizada. Explique por que timeout e validação de esquema são necessários.

# Criar APIs com FastAPI
## Servidor que atende rotas
FastAPI liga caminhos HTTP a funções Python e usa anotações para validação e documentação. Instale no projeto com `uv add fastapi` e servidor de desenvolvimento conforme guia oficial. O primeiro serviço deve rodar localmente, em pasta de laboratório. Uma API pública exige mais: autenticação, TLS, logs, limites, testes, backups e implantação revisada. Não exponha servidor de desenvolvimento diretamente à internet.
## Rota mínima
```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/saude")
def saude():
    return {"status": "ok"}
```
O decorador associa `GET /saude` à função. FastAPI transforma dicionário em JSON. Uma resposta “ok” comprova que a rota respondeu, não que banco, fila e dependências estão saudáveis. Documente o que cada rota promete. Teste localmente antes de adicionar banco ou autenticação.
## Entrada validada
Parâmetros de caminho, query e corpo são fontes de dados não confiáveis. Modelos Pydantic podem declarar campos, tipos e restrições, oferecendo erros úteis. Validação de formato não substitui regra de negócio: preço positivo, estoque suficiente e direito de acesso exigem lógica própria. Não use modelos de banco diretamente como resposta pública se contêm dados internos ou pessoais.
## Status e erros
Retorne códigos HTTP coerentes: 404 para recurso não encontrado, 400 ou 422 conforme tipo de erro de entrada, 500 para falha interna não tratada. Não entregue traceback ou segredo ao cliente. Registre a falha com contexto protegido. Testes devem verificar corpo e status. Uma API que sempre responde 200 com texto “erro” dificulta clientes e monitoramento.
## Dependências e camadas
Separe rota, regra e persistência. A rota traduz HTTP para chamada de função; regra calcula ou valida; repositório lê e grava dados. Essa divisão facilita testar regras sem iniciar servidor e trocar banco sem reescrever toda interface. FastAPI oferece injeção de dependências, útil quando camadas ficam reais. Não crie arquitetura enorme antes de precisar dela.
## Testar sem publicar
Um cliente de teste pode chamar rotas em memória. Teste sucesso, recurso ausente, entrada inválida e autorização. Use banco de treino isolado e dados descartáveis. Quando muda esquema de resposta, consumidores podem quebrar; versionamento e comunicação importam. Documentação interativa ajuda explorar, mas não substitui contrato estável e exemplos de erro.
## Verifique e pratique
Desenhe fluxo navegador → rota → regra → dado → resposta. Implemente localmente uma rota de cálculo sem banco e teste duas entradas, uma inválida. Na atividade do livro, escreva apenas a função de regra que a rota chamaria; o corretor avalia sem iniciar servidor. Explique por que validação e autenticação são responsabilidades diferentes.

# Bots, navegador e agendamento
## Bot é automação com limites
Um bot executa passos sem supervisão contínua: consulta dados, aplica regra e talvez age. Ele precisa de objetivo, autorização, limite de ações, logs e caminho de parada. Comece com bot que apenas lê e produz relatório. Nunca automatize envio de mensagens ou mudanças externas sem definir quem autorizou, destinatários e critérios. Um bug repetido por agendamento pode causar dano maior que um erro manual.
## Playwright para interface
Playwright controla navegador para testar ou automatizar uma interface quando API adequada não existe. Instale `playwright` e os navegadores conforme documentação oficial. Use seletores semânticos, como papel e nome acessível, em vez de coordenadas frágeis. Espere estado observável, não tempo fixo arbitrário. Respeite termos do serviço, privacidade e limites. Uma API oficial costuma ser mais estável que clicar na tela.
## Exemplo local de leitura
```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("http://localhost:8000")
    print(page.title())
    browser.close()
```
Execute apenas contra servidor local de treino criado por você. Um script que funciona na sua tela pode falhar com login, rede lenta ou mudança de layout. Não contorne CAPTCHA ou controles de segurança. Teste falha de navegação e fechamento do navegador.
## Agendar sem duplicar
Cron, systemd timer ou APScheduler podem disparar tarefas em horários definidos. Escolha uma fonte de agendamento; duas instâncias podem duplicar envio. Registre identificador único da execução e use operação idempotente quando possível. Em tarefa periódica, limite duração e sobreposição. Teste numa frequência curta com dados fictícios, depois configure horário real considerando fuso e dias especiais.
## Fila, retry e observação
Se a ação falha, o bot precisa saber se pode tentar de novo sem criar duplicata. Uma fila com confirmação, chave de idempotência e política de tentativas ajuda em sistemas maiores. Para um script simples, arquivo de estado e logs podem bastar, se recuperáveis. Alerta deve informar qual tarefa falhou, quando e qual passo manual é seguro. Não esconda exceções para que o agendador mostre apenas “sucesso”.
## Bots em empresas
Automação pode reconciliar planilhas, classificar solicitações ou gerar relatórios, mas precisa de dono, documentação, revisão de acesso e teste de saída. Meça tempo poupado e taxa de erro, não apenas número de execuções. Faça piloto com dados fictícios ou autorizados e humano revisando resultados. Bots que tomam decisões sobre pessoas exigem critérios claros e supervisão adequada.
## Verifique e pratique
Desenhe um bot que lê pedidos fictícios e prepara resumo sem enviar nada. Liste entrada, regra, limite, log e parada. Na atividade, implemente uma função que seleciona tarefas pendentes de uma lista de dicionários. Depois, se usar Playwright localmente, teste apenas sua própria página de treino. Explique por que repetição automática de `POST` pode criar duplicatas.
