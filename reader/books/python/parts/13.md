# SQLite e SQLAlchemy
## Dados duráveis precisam de regras
Listas e dicionários somem ao encerrar o processo. Um banco guarda dados e permite consultas e transações. SQLite acompanha Python, funciona em arquivo e é ótimo para aprender ou aplicações locais. Sistemas com várias máquinas e concorrência alta podem pedir outro servidor de banco. Comece modelando entidades, identificadores e relações antes de escolher biblioteca. Backup e migração são parte do desenho.
## Consulta parametrizada
```python
import sqlite3

with sqlite3.connect(":memory:") as conexao:
    conexao.execute("CREATE TABLE tarefas (id INTEGER, titulo TEXT)")
    conexao.execute("INSERT INTO tarefas VALUES (?, ?)", (1, "Estudar"))
    linhas = conexao.execute("SELECT titulo FROM tarefas WHERE id = ?", (1,))
    print(linhas.fetchone())
```
Os parâmetros `?` separam dados da instrução SQL. Não monte consulta concatenando texto recebido de usuário; isso permite injeção SQL. O banco em memória desaparece ao terminar. Troque o título por um texto com apóstrofo e execute novamente: a consulta parametrizada continua tratando o título como dado. Depois explique o que seria necessário mudar para persistir o banco entre execuções.
## Transação é unidade
Uma transação agrupa mudanças que devem acontecer juntas. Transferir saldo entre contas exige debitar e creditar como unidade; executar só metade deixa dados inconsistentes. `commit` confirma, `rollback` desfaz mudanças pendentes. `with sqlite3.connect(...)` ajuda a controlar transações, mas fechamento da conexão deve ser entendido conforme versão e uso. Teste falha no meio e confira estado final.
## ORM sem esquecer SQL
SQLAlchemy mapeia objetos e consultas a operações de banco. Instale com `uv add sqlalchemy` e siga o tutorial da versão escolhida. `Session` representa unidade de trabalho; `select` constrói consulta. ORM não elimina necessidade de conhecer índices, cardinalidade e transações. Um código que percorre mil objetos e faz uma consulta por objeto pode ser lento apesar de parecer elegante.
## Migrações e esquema
Quando um campo muda, dados existentes precisam de migração. Em projeto SQLAlchemy, Alembic é ferramenta comum para versionar alterações de esquema. Revise o script gerado, faça backup e teste numa cópia antes de produção. Uma migração que funciona num banco vazio pode falhar ao encontrar dados antigos. Documente como voltar ou recuperar quando alteração não é reversível.
## Índices e consultas
Um índice acelera certas buscas e custa espaço e trabalho na escrita. Meça consulta relevante antes de criar índices indiscriminadamente. `EXPLAIN QUERY PLAN` em SQLite ajuda a observar plano. Filtrar no banco costuma evitar carregar milhões de linhas em Python. Ainda assim, uma consulta rápida pode devolver dado incorreto se a relação entre tabelas foi modelada mal.

Na atividade do navegador, simule em lista de dicionários a mesma regra de filtro; depois execute a versão SQLite localmente. Explique o que uma transação protege e por que ORM não substitui entender SQL.

# Python em produção e em empresas
## De script a produto
Uma empresa precisa saber quem usa o programa, qual problema resolve, onde roda, como é atualizado e quem responde por falhas. Um script que funciona no notebook pode depender de arquivos locais e credenciais pessoais. Separe configuração, código, dados e segredos. Descreva contrato de entrada e saída, limite de carga, custo e plano de recuperação. Construa em etapas verificáveis com usuários reais autorizados.
## Empacotar projeto
`pyproject.toml` declara metadados e dependências. UV pode criar ambiente, lock e executar testes; consulte documentação oficial para comandos da versão instalada. Use controle de versão, README, licença apropriada e instruções de execução. Um lock ajuda reproduzir versões, mas não prova que dependências são seguras. Revise atualizações e artefatos de origem antes de implantar.
## Pipeline de qualidade
Integração contínua pode rodar formatação, lint, tipos e testes a cada mudança. Use a mesma ordem localmente para encurtar feedback. Ambiente de teste deve usar dados descartáveis e credenciais limitadas. Um pipeline verde diz que verificações definidas passaram, não que a aplicação nunca falhará. Adicione teste de jornada essencial e revisão humana para publicação de alto impacto.
## Implantação e observação
Para uma API, acompanhe versão, configuração, migrações, logs, métricas e alertas. Faça publicação gradual quando possível, teste saúde e esteja pronto para reverter. Logs precisam de identificador de requisição e proteção de dados pessoais. Monitore resultado de negócio, não só CPU. Um serviço “no ar” pode devolver respostas erradas, gerar duplicatas ou atrasar tarefas sem disparar erro técnico.
## Segurança e limites
Valide entrada, limite tamanho de arquivo e tempo de execução, use permissões mínimas e atualize dependências. Nunca confie em texto de cliente para construir comando de shell ou SQL. Bibliotecas externas e bots recebem acesso conforme escopo necessário. Uma solução empresarial também deve considerar privacidade, retenção, auditoria e quem aprova automatizações que afetam pessoas ou sistemas.
## Trabalho em equipe
Pull requests, revisão de código, testes e documentos de decisão permitem que outra pessoa mantenha o projeto. Mensagens de commit devem explicar mudança; documentação deve mostrar como executar, testar e recuperar. Evite conhecimento preso na cabeça de um único autor. Design de software inclui comunicação. Uma regra simples escrita em função pequena com testes pode valer mais que arquitetura elaborada sem dono.
## Verifique e pratique
Escolha um bot ou API fictícia para empresa. Escreva problema, usuários, entradas, saídas, dados sensíveis, testes, métrica de sucesso e plano de falha. Na atividade interativa, implemente uma função de regra isolada que seria chamada pelo serviço. Explique o que precisaria ser acrescentado para colocar essa função em produção com segurança.

# Projeto final: do algoritmo ao serviço
## Escolha um problema pequeno
Construa um organizador de tarefas ou despesas fictícias. A primeira versão roda no terminal e usa lista de dicionários. Defina três operações: criar, listar e resumir. Escreva entradas e saídas, casos limite e uma regra que possa ser testada como função. Não comece por interface web ou machine learning; prove que a lógica é útil antes de ampliar o projeto.
## Organize o código
Separe modelo, regras, entrada/saída e testes em módulos coerentes. Use ambiente virtual e dependências declaradas. Crie README com instalação, uso e exemplos. Uma estrutura pequena é suficiente; pastas demais podem esconder a regra central. Faça commits após cada etapa funcional. Execute testes em ambiente limpo para descobrir dependências implícitas.
## Evolua a persistência
Quando a versão em memória funciona, salve em JSON para exercitar formatos e depois experimente SQLite. Migre dados de treino e teste falha no meio da operação. Não use dados pessoais reais. Se adicionar ORM, compare consulta SQL equivalente. Mostre que a regra de resumo devolve mesmo resultado antes e depois de mudar armazenamento.
## Uma API opcional
Crie rota FastAPI que chama as funções já testadas, sem duplicar regra dentro da rota. Valide entrada e status. Use cliente de teste antes de abrir navegador. Mantenha servidor em localhost. Para interface pública, seria necessário plano de autenticação, proteção de dados, TLS, backup e monitoramento; não publique projeto didático sem esses passos.
## Relatório com dados
Com dados fictícios, faça tabela pandas e um gráfico Matplotlib que responde pergunta clara, como tarefas concluídas por semana. Registre origem, período e critérios de limpeza. Compare resumo pandas com função Python padrão para detectar divergência. Não acrescente modelo de ML apenas porque está no livro; use-o somente se houver pergunta preditiva, dados suficientes e avaliação adequada.

Esse registro mostra maturidade melhor que uma lista enorme de funcionalidades inacabadas.
